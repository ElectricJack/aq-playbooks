# AQ host catalog 2.2.0

This bundle lets a playbook route a task. It can read the facts of a task
(`work.read`), ask a model a classification with several fields at once
(`judgment.assess`, answered by `aq.judgment.assessed`), and write the route
(`work.route`). A run starts when a task needs a route (`aq.work.route_needed`).

2.2.0 only adds contracts. All twelve commands and nine events of 2.1.0 are
byte-identical, so an artifact sealed on 2.1.0 pins exactly the same contracts
here. 1.0.0, 2.0.0 and 2.1.0 stay frozen beside it.

The layout matches 2.1.0:
- `registry.json` is the serialized `aq_playbooks_model::Registry`. It is
  generated by `write_catalog_v2_2` in
  `crates/aq-playbooks-cli/tests/catalog_v2_2_contract.rs`, and a test checks
  that the committed bytes are what the generator writes.
- `manifest.json` holds the version, the fingerprint and the vocabularies, plus
  `supersedes` (2.1.0), `commands_added` and `events_added`.
- `fixtures.json` holds:
  - the valid and invalid `cases`;
  - `assessed_guarantee`, the rule for a `judgment.assess` answer;
  - the `compatibility` section: the 2.1.0 base, the unchanged and added
    fingerprints, and no changed command.

Fingerprint: `sha256:0eeb058e4ecbf1b89f2982dce595b327e879914d0737a959d30e183a5e4a2ef7`,
which is `aq_playbooks_model::digest(&("2.2.0", &registry))`.

All five new contracts are version 1.0.0, in scope `project`, with a
64 KiB payload bound (`max_payload_bytes` 65 536). The events come only from
`aq.host.bridge@1` and are kept for 24 hours. Each command needs the
capability of the same name.

## How a routing playbook uses them

1. On `aq.work.route_needed`, start with the event's `subject` as input.
2. `work.read` the task. On `observed`, `task.facts` holds what the document
   can talk about.
3. `judgment.assess`: ask for the fields the document needs a model for (for
   example kind of work and risk) and the yes/no flags (for example "narrow").
   Its `accepted` edge binds the handle.
4. Join the handle under a key, accepting only `assessed`. On `completed`,
   `answer.<key>.output.labels.0` is the first field's label,
   `labels.1` the second, and `flags` the flags that hold. See "Ask, then read
   the answer" in `crates/aq-playbooks-model/FORMAT.md`.
5. Compute the level and who may take the task with `lookup` and `let`, and
   `work.route` it with `subject` set to `task.subject`.
6. On every way the judgment can fail (`no_match`, `timeout`, the invoke's own
   `assessed`/`failed`/`refused` edges and `on_error`), write a fallback route
   that does not read the answer.

A complete example is `crates/aq-playbooks-cli/tests/data/routing_draft.json`.
It is the owner's routing document written as a draft. The contract test
checks it against this catalog and evaluates its routes.

## `work.read` 1.0.0: the facts of a task

An observation (`recovery: observation`), so it is safe to repeat. Deadline
10 s. `reference` and `subject` are public result fields.

**Input.**

| Field | Meaning |
| --- | --- |
| `subject` | `{id, revision}` of the task. The host reads the task as it is now, whatever revision you pass. |

**Outcomes.**

- `observed`: `{reference, subject, facts}`. `subject` carries the task's
  **current** revision. Pass this subject, not the trigger's, to
  `work.route` and `judgment.assess`. A change after this read then makes the
  route `stale` instead of silently applying to a different task.
  Next: classify, or route straight from the facts.
- `refused`: `{reference, subject, reason}`. End the run. Nothing is
  wrong with the playbook.
  - `unknown_task`: there is no such task;
  - `not_on_router`: the task's project is not routed automatically, for
    example because the project is pinned to a named profile.

**`facts`**, all required except `level_hint`:

| Field | Type | Meaning |
| --- | --- | --- |
| `kind` | string ≤ 64 B | The kind of work as whoever filed the task gave it, for example `bugfix`; `""` when none was given. It is a claim, not a classification. |
| `title` | string ≤ 512 B | The task's title, clipped. |
| `description` | string ≤ 8192 B | The task's description, clipped. |
| `origin` | `owner`, `agent`, `supervisor`, `playbook`, `unknown` | Who filed the task. |
| `level_hint` | string ≤ 64 B, **optional** | The level whoever filed the task asked for, such as `standard-high`. Absent when none was asked for. A `lookup` on it takes its default when it is absent. |
| `charged_failures` | integer 0..1000 | Earlier attempts that failed for a real reason and were charged to the task: failed verification, the agent giving up. Owner or service stops, outages, lost workers and review feedback on finished work are not counted. |
| `ended_attempts` | integer 0..1000 | Earlier attempts that ended, for any reason. |
| `route` | `none`, `router`, `owner` | Who set the task's current route, if anyone. A route set by the owner is never replaced, and `work.route` refuses with `owner_route`. |

`facts` has no priority and no provider load. A routing playbook must never
choose by them, so it cannot read them. The object is closed: the host must
not add fields.

## `work.route` 1.0.0: write the route

A mutation, replayed only with its idempotency key (`keyed_idempotent`).
Deadline 10 s. `reference` and `subject` are public result fields.

**Input**, all fields required:

| Field | Type | Meaning |
| --- | --- | --- |
| `subject` | `{id, revision}` | The task, at the revision the playbook decided on. Use `task.subject` from `work.read`. |
| `level` | string ≤ 64 B | Parent and effort, one of the levels Settings offers, for example `standard-high`. |
| `harnesses` | ≤ 16 strings ≤ 64 B | The harnesses that may take the task, such as `claude`, `codex`, `opencode`. An empty list means no restriction. |
| `providers` | ≤ 16 strings ≤ 64 B | The providers that may serve the task, such as `anthropic`. An empty list means no restriction. |
| `prefer` | ≤ 16 strings ≤ 64 B | Harnesses to try first among the allowed ones, in order. Empty: no preference. |
| `hold` | boolean | `true`: the task waits for an allowed harness or provider and never goes elsewhere. Use it when the document says to wait for a particular agent, or when nothing allowed could ever take the task (give the reason `nothing_allowed`). `false`: placement may fall back within the route as usual. |
| `reasons` | ≤ 16 `{code, detail}` | Why: every choice that set, raised or lowered the level and every limit on who may take the task. `code` is one of the codes below. `detail` (≤ 400 B) is a fixed sentence from the playbook, shown on the task. A playbook cannot build text, so write one sentence per situation. |
| `classification` | `{labels, flags, rationale}` or `null` | The judgment the route was based on, recorded with the route. Copy `labels`, `flags` and `rationale` from the `assessed` answer. `null` when there was none. |

The fixed reason codes:

| Code | Use it when |
| --- | --- |
| `level_from_kind` | The level is the one the kind of work gets. |
| `hint_respected` | The level whoever filed the task asked for was used. |
| `hint_capped` | The level asked for was above what the task may have, so it was lowered. |
| `level_lowered` | The level was lowered for any other reason the document gives. |
| `escalated_after_failure` | The level was raised because an earlier attempt failed (`charged_failures`). |
| `raised_for_risk` | The level was raised to the least level the risk requires. |
| `risk_assumed` | The risk or the kind of work could not be worked out, so a default was assumed. |
| `classification_failed` | The judgment failed, was refused, or did not answer in time. |
| `harnesses_limited` | Only some harnesses or providers may take the task. |
| `harness_preferred` | Some harnesses are to be tried first (`prefer`). |
| `harness_excluded` | A harness was left out on purpose. |
| `held_for_harness` | The task waits for an allowed harness instead of going elsewhere (`hold`). |
| `nothing_allowed` | Nothing the document allows could ever take the task. |

The host checks the route against what Settings offers, writes the route
record (spec 0011 §3) with the artifact's digest, and keeps every earlier route.

**Outcomes:**
- `routed`: `{reference, subject}`. The route is written. End the run.
- `stale`: `{reference, subject}`. The task changed after it was read, so
  nothing was written. End the run. The host asks for a route again for the
  new version.
- `refused`: `{reference, subject, reason}`. Nothing was written. End the run
  as unservable. The host, not the playbook, raises it for the owner.
  - `not_offered`: Settings offers no profile for `level`, or no profile at
    that level lists a named harness or provider;
  - `owner_route`: the owner has set this task's route;
  - `not_on_router`: the task's project is not routed automatically;
  - `unknown_task`: there is no such task.

## `judgment.assess` 1.0.0: a structured classification

An asynchronous mutation (`keyed_idempotent`, admission deadline 60 s, not
cancellable). The host runs it as internal work and answers with
`aq.judgment.assessed`, correlated by `operation`. The reconciliation command
is `operation.get`. The `budget` is the host's own bound on the answer.

**Input**, all fields required:

| Field | Type | Meaning |
| --- | --- | --- |
| `subject` | `{id, revision}` | The task being judged. Use `task.subject`. |
| `question` | string ≤ 4096 B | What to judge, in the document's own words, including its definitions. |
| `context.items` | ≤ 16 `{label ≤ 128 B, text ≤ 8192 B}` | What the model sees, such as the title and description from `work.read`. |
| `fields` | ≤ 16 `{id ≤ 64 B, description ≤ 1024 B, choices}` | Each field the model must answer, with up to 64 `choices` (≤ 128 B each). Include a choice such as `unknown` when the document says what to do if it cannot be told. |
| `flags` | ≤ 32 `{id ≤ 64 B, description ≤ 1024 B}` | Yes/no properties. The model says which hold. |
| `rationale_max_bytes` | integer 0..4096 | How long the model's explanation may be. |
| `budget.deadline_ms` | integer 1000..600000 | How long the host may take to answer. |
| `budget.max_output_tokens` | integer 1..65536 | The model's output bound. |

The whole request must fit in 65 536 B, or the host refuses it.

**Outcomes:**
- `accepted`: `{handle}`. The question is queued. Join the handle by its
  binding (`{"op":"ref","root":"j"}`) and accept only `assessed`.
- `assessed`: `{reference, subject, labels, flags, rationale, provenance}`.
  - `labels` (≤ 16 strings ≤ 128 B) has **exactly one label per requested
    field, in field order**: `labels.0` answers `fields[0]`, and each label is
    one of that field's `choices`.
  - `flags` (≤ 32 strings ≤ 64 B) lists the requested flags that hold, each
    once. Test one with `contains(answer.c.output.flags, "narrow")`.
  - `rationale` is at most `rationale_max_bytes` long.
  - `provenance` is the provider record, as in 2.1.0 `judgment.request`.
- `failed`: `{reference, subject, reason}`. Route on the fallback path.
  - `indeterminate`: the model's answer cannot meet the `assessed` rule;
  - `provider_error`: the provider answered with an error;
  - `provider_unavailable`: no permitted provider could be reached;
  - `deadline_exceeded`: no answer within `budget.deadline_ms`.
- `refused`: `{reference, subject, reason}`. Route on the fallback path.
  - `invalid_request`: for example, over 65 536 B, duplicate field ids, or a
    field without choices;
  - `budget_exceeded`: the budget is more than the host allows.

**Host guarantees.**
- **The assessed rule.** An answer that misses a label, has a label that is
  not one of the field's choices, puts labels out of order, has extra labels,
  or names a flag that was not requested is `failed` with `indeterminate`,
  never `assessed`. A playbook reads labels by position, so a missing label
  must never look like a default. `fixtures.json#assessed_guarantee` holds the
  rule with one conforming and seven non-conforming answers.
- **Exactly one completion.** Every accepted judgment gets exactly one final
  completion, `assessed`, `failed` or `refused`, as an `aq.judgment.assessed`
  event. This includes `failed` with `deadline_exceeded` when the host's own
  deadline passes. The engine does not bound a run that waits for it.
  A playbook's join deadline only decides when the run stops waiting.

## Event `aq.judgment.assessed` 1.0.0

The completion of `judgment.assess`. Payload `{outcome, output}`:
`outcome` is `assessed`, `failed` or `refused`, and `output` is that outcome's
output. Correlation field `operation`. The subject is `output.subject.id` and
the revision `output.subject.revision`. A playbook does not wait on it
directly. It joins the handle, which types `output` per outcome.

## Event `aq.work.route_needed` 1.0.0

Emitted by the server when a ready task whose project is routed automatically
has no route, again at most every two minutes while that stays true, and when
the task is retried or reopened. The payload is only `{subject}`, the task's
`{id, revision}`, with subject `subject.id` and revision `subject.revision`.
There is no correlation field. A trigger has no guard, so every emission
starts a run. When to route is the host's rule, not the playbook's.

## What stays with the host

Some sentences of a routing document are the host's behaviour, not
something the playbook says:
- holding a task until something allowed can take it (placement);
- raising a task nothing could ever take to the owner (the server's W6
  failure path, after `refused` or `hold` with `nothing_allowed`);
- when a route is needed (`aq.work.route_needed`);
- never choosing by priority or load (`work.read` does not expose them);
- which model a harness runs at a level (a route names harnesses, not models);
- which failures count (`charged_failures`);
- writing the decision on the task (the route record, from `reasons` and
  `classification`).

## Vendoring

Vendor this directory as a new catalog profile in aq-server, for example
`vendor/aq-host-catalog-2.2.0/` (Host9), from an exact aq-playbooks revision,
pinned to this manifest's fingerprint. Leave the 1.0.0, 2.0.0 and 2.1.0 vendor
copies unchanged. Host8 artifacts validate against it unchanged. See
`docs/aq-host-integration.md` ("AQ host catalog 2.2.0").

To verify:

```sh
cargo test --locked -p aq-playbooks-cli --test catalog_v2_2_contract
```

To regenerate after changing the generator (then review the diff):

```sh
cargo test --locked -p aq-playbooks-cli --test catalog_v2_2_contract -- --ignored write_catalog_v2_2
```
